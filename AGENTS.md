# pgoell-claude-tools

A plugin marketplace containing shared skills for Claude Code, Codex, and Cursor.

Claude Code, Codex, and Cursor use separate plugin metadata, but they must reuse the same skill directories. Do not duplicate `SKILL.md` files for another runtime. The Cursor metadata is generated from the other two; never edit it by hand (see the "Cursor manifests are generated" Design Decision).

Each Design Decision below states the rule only. Its reasons and history live in `docs/explanation/`; read them before changing a rule, not to follow one.

.agents/
  plugins/
    marketplace.json        # Codex plugin registry (local source, policy metadata, interface)

## How to Develop a New Skill

> **Tip:** `agent-system-management:creating-skills` automates this workflow (scaffolding, eval loops, pressure tests, description tuning). The steps below remain the canonical reference.

### 1. Plan the skill

- Identify the CLI tool or API the skill wraps.
- Call the CLI or `curl` directly in the skill. No wrapper scripts around an existing CLI; shipped code is allowed only when it does real work (see the "Skills may ship code" Design Decision), and a skill may tell the agent to write a one-off script at runtime.
- Define operation tiers: Tier 1 (Read), Tier 2 (Write), Tier 3 (Manage/Admin).

### 2. Create the plugin structure

To add to an existing plugin, add `skills/<service>/`. For a new plugin, create `plugins/<plugin-name>/.claude-plugin/plugin.json`:

```json
{
  "name": "<plugin-name>",
  "version": "0.1.0",
  "description": "<one-line description>",
  "author": { "name": "Pascal Göllner" },
  "license": "MIT",
  "keywords": ["<relevant>", "<keywords>"]
}
```

and `.codex-plugin/plugin.json`, which must point at the shared skills folder:

```json
{
  "name": "<plugin-name>",
  "version": "<same-version-as-claude-plugin>",
  "description": "<one-line description>",
  "author": { "name": "Pascal Göllner" },
  "license": "MIT",
  "keywords": ["<relevant>", "<keywords>"],
  "skills": "./skills/",
  "interface": {
    "displayName": "<Plugin Display Name>",
    "shortDescription": "<short human-facing description>",
    "longDescription": "<long human-facing description>",
    "developerName": "Pascal Göllner",
    "category": "Productivity",
    "capabilities": ["Interactive", "Write"],
    "defaultPrompt": ["<starter prompt>"],
    "screenshots": []
  }
}
```

Register the plugin in both marketplaces: `.claude-plugin/marketplace.json` (Claude Code) and `.agents/plugins/marketplace.json` (Codex; each entry must include `interface.displayName` and `interface.shortDescription`). Then run `mise run sync-cursor-manifests` for Cursor. A plugin with no `skills/` yet stays unregistered (see "Unregistered plugin directories").

### 3. Write SKILL.md

Both Claude Code and Codex read it. Follow this structure:

```markdown
---
name: <service>
description: Use when the user wants to <what this skill does>
---

# <Service> Skill

<One-line description>

---

## Auth Approach

<Lazy auth: do not check upfront, just run the command. Diagnose auth failures in Self-Healing>

## Tool Preference

<What tools to use and in what priority order>

## Operations: Tier 1 (Read)

<Read-only operations with exact commands>

## Operations: Tier 2 (Write)

<Create/update operations with exact commands>

## Operations: Tier 3 (Manage)

<Admin/destructive operations with exact commands>

## Self-Healing

<What to do when commands fail (help flags, schema inspection, error codes)>

## Behavioral Guidelines

<How Claude should infer intent and pick operations>
```

Key principles:

- **Exact commands.** Copy-pasteable commands, not pseudocode.
- **Auth is lazy.** Run the operation first, diagnose auth failures in Self-Healing. Never print credential values.
- **Prefer helpers over raw API** when the CLI has convenience commands.
- **Confirm before destructive ops.** Always ask before deleting.
- **Platform-aware tool names.** When a skill uses orchestration tools, include a short Claude Code and Codex mapping instead of hardcoding one runtime.
- **Self-healing is critical.** Tell the agent how to debug failures.

### 4. Add reference docs

Put query syntaxes, format references, recipes, or HTML templates in reference files, linked from SKILL.md as `See <filename>` or `See references/<filename>`. Two layouts coexist:

- **Flat** (`<service>-<topic>.md` next to `SKILL.md`): legacy, used by `gmail`, `calendar`, `jira`, `confluence`, `claude-codex-bridge`, `research`, `visualizing-options`, and `databricks-core`. Fine for one or two short files. Verbatim ports keep the upstream layout; never refactor a port into `references/`, because that breaks the per-file `NOTICE` mapping.
- **`references/` subdirectory**: the modern convention and the choice for new skills. Required when a skill bundles HTML templates, several long references, or any non-markdown asset.

### 5. Update docs and AGENTS.md

The README is a front page; the docs live in `docs/`. A new plugin updates, in one commit:

1. `README.md`: one line under `## Plugins` linking the plugin's reference page, and the plugin count in the first paragraph.
2. `docs/reference/plugins/<name>.md`, plus entries in `docs/reference/plugins/index.md`, `docs/reference/skills.md` and `docs/reference/runtimes.md`.
3. A setup how-to under `docs/how-to/`, listed in `docs/how-to/index.md`, only if the plugin needs setup (no page means no setup).
4. The `README.md` install notes, only if the install command differs from the usual one.
5. A dated entry in `docs/log.md`.
6. A line in "Current Plugins" above.

Then run `mise run sync-cursor-manifests`, or add the plugin to that task's `EXCLUDE` list with a reason. These sites come on top of the version-bump sites ("Every plugin change bumps version"), in the same commit.

A new skill in an existing plugin updates `docs/reference/plugins/<plugin>.md`, `docs/reference/skills.md`, and `docs/log.md`, plus two sites nothing tests: the plugin's own `README.md` `## Skills` list (if it has one) and, for workbench, the skill list in the "One skill per service" Design Decision. Check those by hand.

## Documentation

User docs live in `docs/`, a Diátaxis tree in Open Knowledge Format v0.2. Read `docs/index.md` first.

- Every page except `index.md` and `log.md` starts with YAML frontmatter: `type`, `title`, `description`, `tags` (a list), `status`. `type` matches the folder: `Tutorial` (`tutorials/`), `How-to Guide` (`how-to/`), `Reference` (`reference/`), `Explanation` (`explanation/`). Quote a value that holds a colon-space.
- Folder `index.md` pages carry no frontmatter: an H1, one short paragraph, a bullet list of pages with one-line descriptions.
- Links between docs pages are bundle-relative (`/reference/plugins/workbench.md`); links out of `docs/` are relative paths (`../../plugins/workbench/README.md`).
- A new or changed page updates its folder's `index.md` and adds a dated entry to `docs/log.md`.
- No AI attribution on any page. The dash lint covers `docs/`: `grep -rnP '[\x{2014}\x{2013}]' docs/` must print nothing.
- Docs describe the code as it is now. A PR that makes a page wrong fixes it in the same PR.
- `mise run check-docs` link-checks `docs/` rooted at `docs/` and spell-checks it with the rest of the repo.

## CI Checks

`.github/workflows/pr-validation.yml` runs six checks on every PR against `master` (backed by `mise`, `lefthook`, and `mise-tasks/*`, also run locally on commit and push): formatting and JSON lint, Conventional Commits, plugin version-bump lockstep, manifest schema validation (also fails when generated Cursor manifests drift), docs links and spelling over `README.md`, `AGENTS.md`, `plugins/` and `docs/`, and Cursor plugin validation. At pilot "Step 8: CI loop", `gh pr view <pr> --json statusCheckRollup` returns these six jobs, not an empty array.

- Lefthook hooks run only where `lefthook install` ran (check `ls .git/hooks`; only sample files means nothing runs). So run `dprint fmt` on every markdown or JSON file you touched, plus the manual greps below, before committing.
- Run `dprint check` bare from the repo root; a path argument makes it find no files.
- `.workbench/` is gitignored but `.workbench/pilot.md` stays force-tracked: stage it with `git add -f .workbench/pilot.md`.
- Nothing tests skill behavior; until evals (see `agent-system-management:creating-skills`) cover a skill, check it by hand. The manual greps (dash lint, frontmatter YAML, invocation syntax) are the only structural gates.

## Design Decisions

### Versions and lockstep ([versions-and-lockstep](docs/explanation/versions-and-lockstep.md))

- **Every plugin change bumps version.** Any change to a plugin's skills, metadata, docs, hooks, agents, or tests bumps its version. New skills are minor; fixes, docs, tests, and description changes are patch unless they change behavior materially. Bump every site in lockstep: (1) `.claude-plugin/plugin.json`, only when it already declares `version` (`atlassian` and `google-workspace` omit it on purpose, because Claude Code reads their version from the marketplace entry); (2) `.codex-plugin/plugin.json`, always; (3) the plugin's `version` in `.claude-plugin/marketplace.json`; (4) the plugin's line in "Current Plugins" in this file. `.cursor-plugin/plugin.json` also holds the version, but `mise run sync-cursor-manifests` writes it from sites 1 to 3: run the task, never edit the file. `.agents/plugins/marketplace.json` holds no version. The bump is per PR, not per commit (with `Squash: yes` in `.workbench/pilot.md` a branch merges as one commit), so a branch that already bumped does not bump again; check with `git diff <base>..HEAD -- plugins/<plugin>/.claude-plugin/plugin.json plugins/<plugin>/.codex-plugin/plugin.json .claude-plugin/marketplace.json AGENTS.md`. Before picking the number, check open PRs and `git worktree list` (and each worktree's uncommitted diff) for a parallel branch bumping the same plugin; whichever ships second bumps again before merge. CI checks sites 1 to 3 and the Cursor manifest; site 4 is not checked, so it is on you.

### Runtimes and manifests ([shared-skills](docs/explanation/shared-skills.md))

- **Codex compatibility is metadata plus platform mapping.** Codex manifests sit beside Claude Code manifests and point at the same `skills` folder. Runtime tool differences go into the shared skill body as a mapping, never into duplicated skill files.
- **Cursor manifests are generated, not written.** `mise run sync-cursor-manifests` builds `.cursor-plugin/marketplace.json` and each `plugins/<name>/.cursor-plugin/plugin.json`; never hand-edit them. From `.claude-plugin/plugin.json`: `name`, `description`, `author`, `license`, `keywords`, `version` (the Codex version when Claude omits it). From the Codex manifest: `displayName` (from `interface`) and `skills` (when set). Plus `homepage` and `repository`. Cursor's schema rejects unknown fields, so add a field to the generator only when `plugin.schema.json` lists it. Cursor-only fields go in the task's `extra_for` function; its one use is workbench's `"hooks": "./hooks/hooks-cursor.json"` (Cursor would otherwise read the Claude Code `hooks/hooks.json`). The `EXCLUDE` list: `deprecated` (frozen archive), `prose-styles` (no Cursor output styles), `guards` (hook needs a `beforeShellExecution` port), `session-title` (sets a Claude Code title), `issue-loop` (drives Claude Code). Upstream-URL entries are skipped (no local folder). Run the task after any manifest change; `validate-plugin-schema` runs it with `--check` and fails on drift, and the `validate-cursor-plugins` job runs Cursor's validator from `.github/cursor-validate/`.
- **A plugin with skills may be registered for Claude Code only when its skills drive Claude Code itself** (`issue-loop`). Keep its `.codex-plugin/plugin.json` with `"skills": "./skills/"`, leave it out of `.agents/plugins/marketplace.json`, and say why in `docs/reference/runtimes.md`. A skill that only names Claude Code tools gets a platform mapping instead. issue-loop's files name the example project (Blattomat) for numbers and faults only; never names of people, hosts, accounts or data paths.

### Repository conventions ([repo-conventions](docs/explanation/repo-conventions.md))

- **Skills may ship code; wrappers around an existing CLI stay banned.** A service skill calls its CLI (`gws`) or raw `curl` with env-var auth (Atlassian) directly. Ship code only for work prose cannot do reliably (layout, geometry validation, rendering, deterministic checks), and only if it (1) runs on a runtime the host has (Node 18+, Python through `uv`) with no install step, dependencies absent or committed; (2) makes no network request at runtime except for an action the user asks for (ports drop update notifiers and telemetry); (3) is driven from `SKILL.md` with exact commands and a fallback for hosts without the runtime; (4) follows the text conventions: dash lint (in string literals, write a backslash-u escape of U+2014 or U+2013, not the character), `NOTICE` attribution, version lockstep. A port runs the upstream test suite on the changed copy and records the result in `NOTICE`. Runtime codegen (the agent writes fresh code per run, as in `exporting-presentations-to-pptx`) is preferred when code must differ per run. Script templates copied into the user's space (issue-loop `assets/*.sh`) are allowed; shipped scripts that can run without a live service get a test beside them (`tests/run.sh`, stub driver, no network) with the last result in the plugin README.
- **Skills are self-contained.** A SKILL.md holds everything the agent needs to use the service, except reference docs it links to.
- **Skill invocation syntax in docs is `/<plugin>:<skill>`, not `/<marketplace>:<skill>`.** Always use the fully qualified form (`/atlassian:jira`); never teach the short `/<skill>` form. `pgoell-claude-tools` appears only in `/plugin install <plugin>@pgoell-claude-tools` and `codex plugin marketplace add pgoell/pgoell-claude-tools`. Audit: `grep -rnE '/pgoell-claude-tools:[a-z]' README.md docs/` must print nothing; `grep -rnE '/(atlassian|google-workspace|research|writing|runtime-bridge|agent-system-management|workbench|terminal|playground|databricks|learning|critique|presentations|diagrams|news|insights|issue-loop|ponytail|emil|vercel|taste-skill|deprecated):' docs/` should match each plugin whose skills the doc names. Keep that list to the plugins with skills in `.claude-plugin/marketplace.json`.
- **Em-dash lint and instruction text.** U+2014 and U+2013 are forbidden in every file: skills, `references/*.html`, vendored CSS and JS, root docs. In markdown, name them by codepoint, never as literals. Repo-wide check: `grep -rnP '[\x{2014}\x{2013}]' plugins/ README.md AGENTS.md`. It is not empty: 14 older tracked files (atlassian, google-workspace, research, runtime-bridge, workbench's visualizing-options, using-workbench references, session-start hook) are accepted debt, plus gitignored databricks research notes. So gate on changed files: `git diff <base>..HEAD --name-only | xargs grep -nP '[\x{2014}\x{2013}]'` must print nothing, and `README.md` and `AGENTS.md` stay clean. HTML body copy may use `&mdash;`, `&#8212;`, `&ndash;`, `&#8211;`. CSS and JS comments have no escape: substitute the character at port time.
- **SKILL.md frontmatter `description:` must not contain a colon-space unless the whole value is quoted.** Frontmatter must be strict YAML; an unquoted colon-space fails with `mapping values are not allowed here`. Rephrase (`Examples:` becomes `For example`) or quote the whole value. Validate by hand: feed the frontmatter to `python3 -c 'import yaml,sys; yaml.safe_load(sys.stdin)'`.
- **Lazy auth, never print secrets.** Never check auth up front: run the operation and diagnose auth failures in Self-Healing. Never print or echo credentials, tokens, or API keys; only test whether they are set (`test -n`).

### Ports and licenses ([ports-and-licenses](docs/explanation/ports-and-licenses.md))

Read the upstream `LICENSE` file itself before any port. Never infer the license from CONTRIBUTING.md, DCO mentions, README badges, or summaries.

- **Upstream-port attribution.** A port from a non-MIT upstream (Apache-2.0, as in `playground`) ships `LICENSE` (this repo's MIT), `NOTICE` (per-file upstream attribution, original license, upstream commit SHA), and a plugin `README.md` with a Credits section linking the source. Drop upstream-only frontmatter such as `license:`. Fetch upstream with `gh api ...?ref=<commit-sha>` so the bytes match the SHA in `NOTICE`. Manifest `license:` says MIT (it covers the plugin's own additions; the Apache files stay Apache per `NOTICE`). Model: `plugins/playground/`.
- **Upstream-port attribution, vendored-LICENSE variant.** Or vendor the Apache-2.0 LICENSE verbatim at `plugins/<plugin>/LICENSE` and declare `"license": "Apache-2.0"` in the manifest (`terminal`). `NOTICE` still maps each file, README still has Credits, and `NOTICE` says which shape was chosen.
- **Upstream with no declared license.** Neither relicense nor refuse: vendor verbatim and state in `NOTICE` that there is no license, with the commit SHA, the author's publishing intent, and that all rights stay with the author. No live example.
- **Upstream with restricted-license upstream (use-scope restriction).** For a license that limits use (the Databricks License: "in connection with Databricks Services"), vendor it verbatim at `plugins/<plugin>/LICENSE-upstream` and ship MIT at `plugins/<plugin>/LICENSE`. `NOTICE` holds the commit SHA, the license name and its limit in one plain sentence, the dash substitution rules applied, the per-file mapping (upstream path to local path), and which files are original MIT work. README Credits names the limit. Remove cross-references to upstream skills that were not ported. Both manifests still say `"license": "MIT"`. Model: `plugins/databricks/` (commit `bf6d932`).
- **Idea adaptation ("steal like an artist") is distinct from a verbatim port.** Rewriting an upstream idea in your own words, copying no text, is original MIT work: ship MIT `LICENSE` and a README `## Inspiration` (or Credits) section naming the source and author, and no `NOTICE` or `LICENSE-upstream` (`learning`). Pasting upstream text makes it a port.
- **Verbatim ports must substitute em-dashes/en-dashes inline at port time.** Rules: (1) sentence pause `<space>U+2014<space>` becomes comma plus space; (2) labelled bullet `**name** U+2014 description` becomes colon plus space; (3) number range `<digit>U+2013<digit>` becomes a hyphen; (4) heading `## Title U+2014 Subtitle` becomes colon plus space; (5) code-block comment `# Label U+2014 Description` becomes colon plus space. Periods, semicolons, parentheses, or a split sentence also work. Record the rules applied in the plugin's `NOTICE` (see `plugins/playground/NOTICE`, `plugins/databricks/NOTICE`). The right arrow (U+2192) stays.

### External and deprecated plugins ([external-and-vendored-plugins](docs/explanation/external-and-vendored-plugins.md), [the-deprecated-archive](docs/explanation/the-deprecated-archive.md))

- **External plugins are referenced by git URL, not vendored.** A marketplace entry may point at an upstream repo (`{"source": "url", "url": "https://github.com/<owner>/<repo>.git"}`; Claude Code also takes `github`, `git-subdir`, `npm`; Codex takes `url`, `git-subdir`; both allow `ref`/`sha` pins). Use it for a permissively licensed upstream whose whole surface you want. The entry has no `version`, no version lockstep, no CI check, no `LICENSE`/`NOTICE`/Credits, and this repo's lint and frontmatter rules do not apply to its files; its `docs/reference/plugins/` page still names the upstream and license, and the other new-plugin docs sites apply (no plugin README). Unpinned means unreviewed upstream code runs on refresh; pin with `sha` when that matters. An upstream with no Codex manifest is registered for Claude Code only, with the reason in `docs/reference/runtimes.md`; one with no manifest at all sets `"strict": false`. Once an upstream ships `.codex-plugin/plugin.json`, read it and its `LICENSE` at a pinned SHA and add it to `.agents/plugins/marketplace.json` too (`taste-skill`). Document external skills by folder name, which is what Claude Code uses, not frontmatter `name:`; Codex uses the frontmatter `name:`, so a plugin page for a Codex-registered upstream also lists the Codex name where the two differ (`taste-skill`). When a vendored port's upstream turns into a permissive plugin repo, swap the port for an external entry.
- **The `deprecated` plugin is a registered, frozen archive.** When a restructure supersedes a skill, move it (SKILL.md plus references) to `plugins/deprecated/skills/<old-name>/` in the same PR that removes it, prefix its description with "Deprecated, superseded by <replacement>.", add a one-line banner under the H1 naming the replacement, rewrite internal cross-references to `deprecated:`, and drop or de-brand assets that must not ship. Move an archived port's `NOTICE` block with it. Never extend a deprecated skill; do not list them in `docs/reference/skills.md`; keep the plugin registered in both marketplaces.

### Skill design patterns ([skill-design-patterns](docs/explanation/skill-design-patterns.md))

- **One skill per service, one plugin per product family.** Gmail and Calendar sit in `google-workspace`; Jira and Confluence in `atlassian`. Exception: workbench ships its peer workflow skills together but split, so each phase runs alone (`pilot`, `using-workbench`, `brainstorming`, `writing-spec`, `writing-plans`, `visualizing-options`, `test-driven-development`, `subagent-driven-development`, `systematic-debugging`, `verification-before-completion`, `crafting-html`, `crafting-design-systems`). `presentations` splits its five life-cycle skills the same way. Skills that need local Unix tools go in `terminal`.
- **Workflow skills are execution protocols.** When a user calls a workflow skill such as `workbench:pilot`, follow its sequence as a procedure (branch setup, brainstorm, spec, plan, pressure test, implementation, verification where they apply), not as loose advice.
- **Agents for long-running, context-heavy operations (forward-looking, currently unused).** The `agents/` slot is reserved for agents a skill would dispatch for context-heavy work. No plugin uses it (`research` runs subagents from prompt templates in `skills/research/`); use skills for everything else.
- **Unregistered plugin directories are a valid stub state.** A `plugins/<plugin>/` folder with both manifests but no marketplace entry is a stub (research notes, scaffolding). To bring it online, add `skills/` with at least one `SKILL.md` and register it in both marketplaces; to retract a plugin, remove it from both. Plugin-level `references/` stays valid after skills ship. Never force-add the gitignored `plugins/databricks/references/research/`.
- **Sibling-skill reference sharing for thin variants (historical pattern, still valid).** A thin variant may read a sibling's references, but every such path must carry the `../<sibling>/references/` prefix (a bare `references/...` resolves against the variant's own folder), and the variant ships no `references/` of its own. Prefer a self-contained `SKILL.md` over a redirect to the sibling's `SKILL.md`. Share only identical infrastructure. Live case: `writing:coach` reads `../ghostwrite/references/pyramid-audits.md`.
- **Producer/renderer skill pairs maintain different taxonomies at different abstraction levels.** The content producer lists argument roles, the renderer lists layout templates; the producer ships a non-binding mapping table, and its type field (`slide_type` in `deck.md`) is a hint, never a constraint. Do not merge the two lists into one enum.

### HTML producers, presets and themes ([html-producers-presets-and-themes](docs/explanation/html-producers-presets-and-themes.md))

- **HTML artifact output is a first-class skill mode.** A single-file HTML producer (`writing-spec`, `writing-plans`, `brainstorming`, `systematic-debugging`, `research:research`) ships an `## Output Format` section with the format and path resolution order, a `references/<artifact>-template.html`, a cross-reference to `workbench:crafting-html` for other artifact types, and an inline `### Applying a design system` block (do not point at `crafting-design-systems` for it). `crafting-html` covers all other standalone HTML artifacts and reads its 20 references lazily. Renaming, adding, or removing a CSS variable in any of the five producer templates' `:root` blocks updates the inventory in `plugins/workbench/skills/crafting-design-systems/SKILL.md` in the same commit; the inventory leaves out `crafting-html`'s references on purpose.
- **Multi-file HTML producers are a distinct shape.** Like `presentations:creating-presentations`: no `## Output Format` section, no `.workbench/config.md`, theming from presets, the runtime shipped as `assets/`, and a cross-reference to `workbench:crafting-html` for single-file artifacts.
- **Artifact exporters are consumers, not producers.** Like `presentations:exporting-presentations-to-pptx`: no `## Output Format`, no `.workbench/config.md`, no inventory entry; read tokens from the artifact (shared CSS, then inline `<style>`, which wins); output paths in its own SKILL.md; producer and exporter cross-reference each other in one sentence, and the exporter's description names the producer.
- **The presentations plugin themes through presets, not design systems, and parameterizes through `.pgoell/presentations/`.** It never reads `.workbench/config.md`. Preset contract: `plugins/presentations/presets/README.md`. Bundled presets live in `presets/` (changing one is a version-bumped change); user-local ones in `.pgoell/presentations/presets/<name>/` of the consuming repo, never shipped. Resolution: prompt choice, then `.pgoell/presentations/config.md` `## Preset` (`Name:` local first then bundled; `Path:` any directory following the contract), then the single local preset (several: ask), then the bundled preset that fits the deck's use per the contract's table, stated with its reason (`default` otherwise). Copy `deck-stage.js`, `presenter.js`, `presenter.html` unmodified next to each deck. Check by hand: example slides embed a synced copy of the preset's variable files (only the `../` prefix on `@font-face` URLs may differ) and make no network requests; every text tier holds 4.5:1 contrast on every surface in both scopes; the dash rule covers `presets/`.
- **The diagrams plugin themes through its own theme contract, derived from presentations presets.** `diagrams:creating-diagrams` never reads `.workbench/config.md` or design systems. Colors come only from a `theme.css` with two `[data-theme]` blocks (contract `plugins/diagrams/themes/README.md`), bundled in `themes/` or user-local in `.pgoell/diagrams/themes/<name>/`. Selection: prompt, then `.pgoell/diagrams/config.md` `## Theme`, then an offer to derive from a configured presentations preset, then `classic`. Derive brand themes from preset tokens or a PPTX `theme1.xml`, never by hand. The fallback template's `THEME:START`/`THEME:END` block is a synced copy of `themes/classic/theme.css`: edit both together. The engine is archify at `1bb61c6` with changes listed in `plugins/diagrams/NOTICE`; a re-port reapplies them, the brand-mark removals and the dash substitution, then runs upstream's tests.

### Workbench routing and configuration ([workbench-routing](docs/explanation/workbench-routing.md))

- **Per-artifact format, path, and design-system resolution via `.workbench/config.md`.** `writing-spec`, `writing-plans`, `brainstorming`, and `systematic-debugging` resolve each independently. Format: prompt, then `## Output formats`, then skill default. Path: `.workbench/pilot.md` `## Documentation paths` (specs and plans only), then `## Output paths`, then default. Design system: prompt, then `## Design system` `Name:`, then none. Defaults: specs `md` in `.workbench/specs`, plans `md` in `.workbench/plans`, brainstorms `html` in `.workbench/brainstorms`, debug reports `html` in `.workbench/debug-reports`. `research:research` ignores config for format and path (HTML at `reports/<topic-slug>-<YYYY-MM-DD>/report.html`) but honors `## Design system`; `crafting-html` reads only `## Design system`. Schema: `plugins/workbench/skills/pilot/references/config-schema.md`.
- **Lane triage defaults to the lighter lane, and a reflex ladder runs before routing.** When unsure between lanes, pick the lighter one; escalate only for a named reason (expensive-to-reverse decision, blast radius beyond the files at hand, real disagreement about intent, a requirement not statable in one sentence without guessing). Two exceptions route heavy: a user who names a spec, plan, or brainstorm is never downgraded, and destructive or hard-to-reverse work (migrations, deletions, auth, public API breaks, money, credentials) always routes heavy. Step 0 runs the reflex ladder (YAGNI, reuse, stdlib, native platform, installed dependency, one-liner); if a rung holds, no lane. State the ladder inline, not by reference. Never edit `using-workbench/references/using-superpowers-upstream.md`. Any new lane rule is lighter-by-default.
- **Optional required-skill rows.** A pilot required-skills row for a plugin the user may lack (`ponytail:ponytail`) is optional: never reported as skipped when absent, may need no call when its hooks inject content, and never overrides a mandatory row (TDD and verification win; precedence in `references/required-skills.md`). Use this shape, never a hard dependency, for cross-plugin rows.

### Plugins without skills ([plugins-without-skills](docs/explanation/plugins-without-skills.md))

- **Output styles are a plugin surface, and a skill-less plugin is a valid shape.** Styles in `output-styles/*.md` set `keep-coding-instructions: true` when they only shape prose (or Claude Code drops its coding prompt). Each style file stands alone, so shared blocks are duplicated on purpose. A skill-less plugin registers in `.claude-plugin/marketplace.json` only, keeps a `.codex-plugin/plugin.json` without `skills` for the version check, gets no `docs/reference/skills.md` rows, and says in `docs/reference/runtimes.md` why Codex lacks it; every other docs site (including a setup how-to, since picking a style is setup), the lint, the version lockstep and strict YAML still apply. Add new prose styles to `prose-styles`, not a new plugin.
