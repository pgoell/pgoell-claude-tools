# Upgrading an old loop folder

`init.sh` never overwrites a file, so a loop folder keeps the scripts of the version that made it.

- A loop folder made by version 0.6.0 or earlier: a finished task with its pane scrolled up sits until `STALLED`. Copy `notify.sh`, `wait.sh` and `next.sh` anew from the skill's `assets/`, all three or none: the old `next.sh` never removes `task.notified`, so a stale line could settle the next task's wait, and the old `notify.sh` never writes it.
- A loop folder made by version 0.2.0 or earlier, or by hand: it has no standing order, so a brief or a takeover may wait for the user's go. In this order: run `init.sh` on it again (it never overwrites; it adds `grant.sh`, `takeover-check.sh` and the two `standing-order` templates), copy `lib.sh` anew from the skill's `assets/`, and go through "The standing order" in `SKILL.md` with the user. Only after the user has run `grant.sh`, copy `next.sh` and `start.sh` anew and take the new clauses of rules 12 and 14 from `assets/rules.md`: the new `next.sh` refuses to send without the order, so until then the old one keeps the loop going, with a go from the user now and then. A hand-made folder with no `loop.env` needs one first: `grant.sh` reads the implementer's name and checkout from it.
- A loop folder made by version 0.1.0: `init.sh` never overwrites, so run it again (it adds `notify.sh`), then copy `next.sh`, `wait.sh` and `lib.sh` anew from the skill's `assets/` and take rule 19 and the new clauses of rules 2, 5, 9 and 12 from `assets/rules.md` into your `rules.md`. Take all of them or none: the new `wait.sh` with the old `next.sh` says `TIMEOUT` only once ever.
